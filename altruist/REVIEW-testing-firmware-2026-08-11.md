## 1. Блокеры до Stable: локальный UI открыт всем в сети

**Наблюдение.** `Configuration → Authentication` — чекбокс **снят**, `User: admin`,
пароль пуст. При этом на том же веб-сервере, без единого запроса пароля, доступны:

- `System → Backup & restore → Download backup` — файл содержит **ключ владельца**
  и служит логином на карту;
- `Restore from backup` — заливка чужого конфига (свой `rws_owner`, свой Wi-Fi,
  свой Custom API);
- `Delete configuration → All settings` — стирание, причём этот вариант предвыбран;
- `Custom → Custom API / InfluxDB` — увод копии данных на произвольный хост.

Всё это по HTTP: даже при включённой аутентификации пароль и сам бэкап идут по сети
открытым текстом.

**Что из этого следует.** Пункт «у кнопки Download backup нет предупреждения» — это
следствие, а не причина. Причина в том, что кнопка вообще никем не защищена.

**Отдельно — `/guest-restore`.** По анонсу он доступен на конфигурационной точке
устройства до присоединения к домашней сети. Поле пароля этой точки на скриншоте
пустое (**требует проверки**: это дефолт «открытая сеть» или просто не отображается
сохранённое значение). Если сеть открыта, то атакующему нужен только радиус приёма —
ни пароля от домашнего Wi-Fi, ни физического доступа. Окно — не минуты: коробка,
которую распаковали и отложили; устройство после `Delete configuration → Wi-Fi only`
(ключ владельца при этом остаётся на устройстве). Заливка своего конфига здесь —
это не порча настроек, а перехват: свой owner, свой Wi-Fi, свой сервер для копии
данных, свой пароль админа.

**Предложения, по возрастанию стоимости:**

1. Требовать аутентификацию хотя бы для трёх операций — `Download backup`,
   `Restore from backup`, `Delete configuration`, — даже когда чекбокс снят.
2. На guest-интерфейсе разрешать восстановление только устройству **без
   сохранённого конфига и без ключа владельца**. Сценарий «удобно сразу после
   полного сброса» сохраняется целиком, захват настроенного устройства исчезает.
3. Предзаполнять пароль конфигурационной точки уникальным значением (поле в UI уже
   есть). Важно: пароль не должен выводиться из ID или MAC — ID и так светится в SSID.
4. Включать `Authentication` по умолчанию либо требовать задать пароль при первом
   входе в System.

**Требует проверки в коде:** есть ли CSRF-токены и проверка заголовка `Host`/`Origin`
на POST-эндпоинтах. Если нет, то при предсказуемом адресе (`altruist-urban-<id>.local`)
любая страница, открытая в браузере пользователя, может вслепую дёрнуть
`Save configuration` / `Restore` / `Delete`, а при отсутствии проверки `Host` —
через DNS rebinding — ещё и прочитать бэкап. Это единственный сценарий, не требующий
присутствия рядом с домом.

## 2. Проблемы

### 2.1. Панель `Data export` в первые минуты показывает неправду

**Наблюдение.** `Robonomics Datalog — OK, SENDS 0/0, LAST N/A` и
`Robonomics Map — ERROR, SENDS 0/1, LAST N/A` при `Uptime 73s`, интервале датолога
600 с и интервале карты 30 с.

Три отдельных дефекта:

1. **Зелёный `OK` при `0/0`.** Это состояние «ещё ни разу не пробовал», а выглядит
   как «всё работает». Ложноположительный статус вреднее отсутствия статуса: человек
   уйдёт со страницы уверенным, что датолог отправляется. Нужен третий статус —
   `Ожидание` / «первая отправка через ~N мин».
2. **`SENDS 0/1` при `LAST N/A`.** Попытка была, а «последняя попытка» пустая:
   счётчик и метка времени обновляются из разных мест, похоже, `LAST` пишется только
   при успехе. Это конкретный баг, чинить раньше, чем добавлять тексты.
3. **`ERROR` без причины.** Ни кода, ни хоста, ни действия.

**Самая сильная зацепка по самой ошибке** — в загрузочном логе строка **`Send to :`
пустая**, прямо перед `Robonomics Address:`. Похоже, целевой хост карты не
разворачивается: `Region = Global`, но подпись обещает «auto from coordinates», а
координаты `0.0,0.0`; `Robonomics Map Host = Default pool (auto)`. То есть пакет,
возможно, вообще некуда слать — это правдоподобнее версии «карта отбивает данные
из-за нулевых координат».

**Дёшево и полезно:** структура на сервис `last_http_code (int16) + last_attempt_ts +
last_ok_ts + fail_count` — около 12 байт на сервис; расшифровку кода в человеческий
текст держать в JS страницы, не во flash. И отдать это в JSON-эндпоинте статуса —
тогда поддержке хватит его и без правок UI.

### 2.2. Автообновление, скорее всего, отменит ручной откат на Stable

**Наблюдение.** `Configuration → System → Auto update firmware` включён,
`Last OTA check 41s` при аптайме 73 с, в конфиге и в `[BUILD]`-строке `channel=testing`.
Установка без Erase конфиг сохраняет.

**Гипотеза, требующая ответа до Stable:** после ручного отката на Stable в конфиге
останется `channel=testing`, и авто-OTA вернёт устройство на Testing. Плюс общий
риск: устройство, оставленное на Testing с этой галкой, молча едет за каждой
CI-сборкой `esp32-dev`.

### 2.3. Устройство с недоступной сохранённой сетью не поднимает точку настройки

**Наблюдение**, из лога: попытка подключения начинается, через ~15 секунд —
`[WiFi] Saved credentials but STA did not connect; skipping config AP (runtime reconnect).`
То есть на загрузке даётся одна попытка, после чего портал настройки не поднимается,
а состояние «сохранённая сеть недоступна» **нигде не видно** — ни в UI (его не
открыть), ни отдельным цветом LED.

Сценарий отказа бытовой: общее отключение питания, роутер поднимается медленнее
датчика. Пользователь ждёт появления сети `Altruist-…` и не дожидается. Симптом
читается как аппаратная поломка, а не как настройка, — люди пойдут в возврат.
**Не проверено:** поднимается ли AP когда-нибудь позже, через десятки минут аптайма.

**Важно — от очевидного решения предостерегаем.** «Поднимать AP автоматически после
N неудач» открывает атаку: заглушить домашний Wi-Fi → устройство само поднимает
открытую точку → на ней `/guest-restore` → захват. Если текущее поведение выбрано
именно поэтому — так и скажите, и тогда это нужно описать в документации, а не менять.

**Если менять, то дёшево и без APSTA:** держать AP параллельно со STA на C6 плохо
(SoftAP форсится на канал STA, каждый скан рвёт клиента). Лучше: после T минут
неуспешных реконнектов ставить флаг в NVS и **перезагружаться** в режим config AP;
успешный коннект флаг снимает. Ещё дешевле: не пропускать AP на загрузке, если
предыдущие N загрузок тоже не подключились.

**Самое дешёвое из всего — индикация.** В логе есть `Setup board RGB led on pin : 8`
и `[Urban LED] mode: : GREEN`. Отдельный цвет для «сохранённая сеть недоступна»
стоит ноль и снимает половину обращений. Тем более что кнопочного пути на этой
сборке Urban, судя по логу, нет вообще: `Can't setup button pin : -1.00` — **требует
проверки**, что это значит для процедуры Wi-Fi-reset, которую мы описываем в
документации.

### 2.4. Скан сетей в Improv возвращает пустой список

**Наблюдение.** В `Configure Wi-Fi` список пуст, по умолчанию `Join other…`; сеть
ввели текстом вручную, подключение прошло с первого раза.

**Вероятная причина видна в логе:** Improv-кадры идут в то же время, что и попытка
boot-time коннекта, а `WiFi.scanNetworks()` в этот момент возвращает пусто.
**Лечение без своего цикла скана:** по первому Improv-RPC прерывать pending-коннект,
запускать асинхронный скан и отвечать из кэша; либо не начинать boot-time коннект,
пока идёт Improv-сессия.

### 2.5. Бэкап: один файл в трёх ролях, без ротации и отзыва

Файл — это одновременно настройки (их не жалко отправить в поддержку), приватный
ключ и логин на карту. Отправить «только безопасную часть» физически нельзя.
Отозвать нельзя: при утечке единственное лечение — сменить identity, то есть
потерять адрес устройства и историю на карте. Средство хуже болезни, поэтому им
никто не воспользуется.

Уточнение к формулировке, чтобы не спорить о лишнем: при **self-owner** (наш случай)
бэкап = полный доступ к данным на карте; при **внешнем owner** он данные не
расшифрует, но позволяет выдать себя за устройство. Секрет в обоих случаях.

**Предложения:** отдельный экспорт «settings only, без ключа» (минимальная версия —
тот же обработчик с `?nokey=1`); опциональный пароль на файл ключа; предупреждение
у кнопки (текст ниже, раздел 5).
**Требует проверки:** попадают ли в бэкап пароль Wi-Fi, пароль админа и креды
Influx/Custom API открытым текстом; не светится ли адрес устройства в имени файла;
обрабатывает ли sensors.map импортируемый бэкап в браузере или грузит на сервер.

### 2.6. `Delete configuration`: опасный дефолт и неясные последствия

**Наблюдение.** Предвыбран `All settings` («Everything stored on the device»), рядом
красная `Delete`. Безопасный `Wi-Fi only` — вторым.

Дефолт перевернуть: сначала `Wi-Fi only`, либо не выбирать ничего и держать кнопку
неактивной. Для `All settings` — модалка с явным текстом про потерю адреса и истории.

**Требует проверки, и это важнее оформления:** стирается ли при `All settings`
ключевой материал из flash или удаляется только конфиг-файл. На LittleFS/NVS с
wear-leveling копии часто остаются — тогда покупатель б/у устройства получает ключ
предыдущего владельца. Это же определяет, годится ли `All settings` как процедура
подготовки к перепродаже и RMA.

### 2.7. Смена owner — передача доступа к данным, а на экране ни слова

**Наблюдение.** `Device group (RWS)`: четыре радиокнопки `Standalone / Create group /
Join group / Manual owner` **без единой строки пояснения**, плюс статус `Pending sync`
без расшифровки. Поле `RWS Owner Address` при этом живёт **на другой странице**, в
карточке ROBONOMICS, со своей кнопкой Save — это ещё и источник рассогласованного
состояния.

`Join group` означает «мастер группы читает мои данные, а я свои — нет». `Manual owner`
с опечаткой в SS58-адресе означает «данные зашифрованы в адрес, которым никто не
владеет, молча и навсегда»; контрольная сумма в SS58 есть, значит валидация возможна —
**требует проверки**, делается ли она.

### 2.8. Ярлык `altruist.local` не совпадает с реальным именем устройства

**Наблюдение.** Зона в сайдбаре называется `altruist.local`, реальное mDNS-имя —
`altruist-urban-0b50` (резолвится), `altruist.local` — таймаут. Уникальные имена
`altruist-urban-<id>` заявлены в этом же анонсе как новая фича, то есть ярлык остался
от прежней модели. В сети, где Altruist больше одного, держать `altruist.local` может
максимум один.

Мелкая внутренняя нестыковка: hostname — короткий `altruist-urban-0b50`, а SSID точки
настройки — полный `Altruist-urban-1051DB010B50`. Один идентификатор в двух формах.

**Предложение:** показывать в ярлыке фактический `Local Hostname` (значение уже есть
в шапке страницы) — правка чистого JS.

### 2.9. Мелочи, которые видит пользователь

- `GPS: Latitude, Longtitude` → **Longitude**.
- «Change it if you have more **then** one Altruist» → **than**.
- Диалог вебфлешера предлагает установить **`airrohr-firmware_en`**. Сам текст
  диалога («All data on the device will be lost») принадлежит esp-web-tools и правится
  только патчем компонента — а вот имя правится одной строкой в манифесте (`name`).
  Предлагаем «Altruist Urban (Testing)», а предупреждение про identity вынести на
  страницу флешера над кнопкой.
- Влияние на ряд: любое сохранение настроек = перезагрузка устройства = дырка в данных.
- Легаси-строки в Influx-дефолтах: `/write?db=sensorcommunity`, measurement `feinstaub`.
- Коллизия имён: «Data export» — это и панель статусов в `Status`, и раздел настроек
  в зоне `Custom`.
- В шапке: `R-URB_2026-07-08-testing+3e2ed16/EN (Aug 7 2026)` — версия названа
  2026-07-08, дата сборки 7 августа. Не баг, но поддержке это придётся объяснять.
- В UI нет самоидентификации датчиков, хотя в логе она есть:
  `Read SDS...: 23-06-26(6717)` — прошивка и серийник SDS011. Для RMA полезно.

## 3. Компоновка UI: что стоит сделать в первую очередь

Разбор по скриншотам, с опорой на обычные вещи — эвристики Нильсена, гештальт-близость,
прогрессивное раскрытие, правила для деструктивных действий.

**Топ-7 по соотношению «эффект / трудозатраты»:**

1. **Одна кнопка Save на страницу, в закреплённом футере, активна только при
   изменениях.** Сейчас на странице устройства она стоит *посреди* — после карточки
   SYSTEM и перед FIRMWARE UPDATE, и непонятно, что именно сохраняет; в Maintenance
   висит там, где сохранять почти нечего; в зоне карты их две с разным названием и
   выравниванием (`Save configuration and restart` и `Save`). Плюс предупреждение при
   уходе с несохранёнными изменениями.
2. **Обезвредить деструктивную зону.** Снять предвыбор `All settings`; убрать
   постоянно висящую карточку «Are you sure you want to restart?» (подтверждение
   должно появляться *после* нажатия, иначе оно приучает игнорировать подтверждения);
   `Restart` перекрасить в нейтральную — красный оставить только `Delete` и
   `Restore from backup`; в модалке восстановления предложить сначала скачать текущий
   бэкап.
3. **Починить группировку в карточке Wi-Fi.** Чекбокс «Check it if WiFi network has
   no password» стоит в левой колонке, а управляет полем `Password` справа — нарушение
   близости, самый заметный дефект формы. `Local Hostname` попал под пароль и читается
   как его часть. В одну колонку: SSID → Password → чекбокс → отдельная карточка
   «Имя устройства в сети».
4. **Строка-вердикт в Overview и человеческие статусы доставки.** Заголовок
   «Is the device running normally right now?» задаёт вопрос, а ответа на экране нет —
   вместо него шесть технических плиток, включая `Reset Reason` и `Free heap before
   reset`, которые тревожат («USB reset (flash/boot)» читается как сбой). Наверх —
   одну строку вердикта, технику — вниз в Technical details.
5. **`Publish to map` и `Encrypt map values` — в одну таблицу метрик** с колонками
   «Публиковать» / «Шифровать». Сейчас это два списка с разной гранулярностью
   (в публикации «Temperature» и «Humidity» отдельно, в шифровании — «climate» одним
   пунктом), разным порядком и словом `Encrypt`, повторённым 11 раз; пользователь
   вынужден сопоставлять их сам.
6. **Переименовать зоны сайдбара.** `altruist.local` — это адрес, по которому
   пользователь уже находится, странно называть так раздел. Зоны построены по разным
   основаниям (два адреса, тип интеграции, класс задач), поэтому правило «что где
   лежит» не выводится. Ярлыки: Device / Public map (sensors.social) / Own server /
   Maintenance.
7. **Типографика заголовков.** Сейчас название страницы визуально слабее карточки
   внутри неё, три уровня подряд набраны капсом и различаются кеглем на пару пикселей.
   Ввести шкалу и оставить капс только на самом мелком уровне; в Readings убрать
   лишний уровень вложенности.

**Следующим заходом:** разрезать зону устройства по уже существующему шву
(«показания и статус» / «настройки»); объединить `RWS Owner Address` с `Device group`
в одну карточку; перенести `Temperature correction` и `SDS measure interval` к
настройкам датчика, а `Auto update firmware` — в карточку Firmware Update; свернуть
Debug в «Диагностику»; GPS разбить на два поля (широта/долгота) с валидацией.

**Мелочи, заметные на скриншотах:** в `Debug level` четыре кнопки (`off / only errors /
min. info / max. info`) не показывают, какой уровень активен — это радиогруппа, а
выглядит как четыре команды; у консоли нет «Копировать» и «Пауза», хотя открывают её
именно за этим; `LED brightness (%)` — поле на всю ширину под число 0–100; зависимые
поля не блокируются, когда чекбокс снят (`Authentication`, `Send data to custom API`);
на странице Device group есть горизонтальный скроллбар — страница шире вьюпорта.

## 4. Не баг прошивки, но бьёт по тестировщикам (Linux)

Порт появляется в диалоге браузера, но открыть его не удаётся:
`Failed to execute 'open' on 'SerialPort'`. Причины обычно две сразу:

1. пользователь не в группе `dialout` (`/dev/ttyACM0` — `root:dialout`);
2. `ModemManager` опрашивает свежий `ttyACM` как модем и держит порт.

Лечится `sudo usermod -aG dialout $USER` (+ `newgrp dialout`, чтобы не перелогиниваться)
и udev-правилом `SUBSYSTEM=="tty", ATTRS{idVendor}=="303a"` → `ENV{ID_MM_DEVICE_IGNORE}="1"`.
Третья частая причина, которой у нас не было: Chromium из snap не получает доступ к
`/dev/ttyACM0` вообще.

**Предложение:** показывать на странице вебфлешера подсказку именно на этот текст
ошибки. Это самый частый способ «не начать» на Linux.

## 5. Готовые формулировки для UI (EN)

**Download backup** — вместо «Download a full backup (settings + owner key)…»:

> A full backup: settings plus the owner key. Treat it like a password — anyone with
> this file can restore this device and open its data on sensors.map. Store it where
> you keep passwords; don't send it in chats or email. Support will never ask for it.

плюс вторая кнопка `Download settings only` — без неё пользователь не может отправить
настройки в поддержку иначе как отдав ключ.

**Delete configuration** — порядок опций поменять, дефолт `Wi-Fi only`:

> **Wi-Fi only** — Forget the saved Wi-Fi network. The device keeps its address and its
> history on the map.
> **All settings** — Everything stored on the device, including its Robonomics address.
> The device will appear on the map as a new sensor, and its existing history stays
> under the old address. Download a backup first if you may want it back.

**Encrypt map values** — добавить вторую фразу, её сейчас нет:

> Checked metrics are readable only by the device owner — log in as owner on
> sensors.map to see them. Unchecked metrics are published in the clear.
> Location, device address and send times stay public either way, so encryption hides
> the readings, not the presence of the device.

**Authentication** (текста нет вообще):

> Protects this page with a user name and password. While it's off, anyone on this
> Wi-Fi network can open these settings, download the backup and change the configuration.

**Device group (RWS)** — по строке под каждым режимом:

> **Standalone** — values are encrypted for this device itself. Its own backup opens
> them on the map.
> **Create group** — this device becomes the group owner. Its key opens data of every
> device that joins.
> **Join group** — values will be encrypted for the group owner. The group owner can
> read them; this device's backup cannot.
> **Manual owner** — values will be encrypted for the address you enter. Check it
> carefully: if the address is wrong, nobody can decrypt them.

## 6. Вопросы разработчику

**Q1. Откат на Stable — три конкретных факта.** Совпадает ли таблица разделов у
Stable `d1623eb` и Testing `3e2ed16` (от этого зависит, безопасен ли наш совет
«обновляйся без Erase» вообще)? Версионируется ли конфиг и какого размера JSON-буфер
у парсера в Stable — переживёт ли он конфиг, записанный Testing (encrypt_* по
метрикам, map host, region, hostname, auth), или упадёт в дефолты и потеряет identity?
Где физически лежит приватный ключ — в том же JSON на LittleFS или в NVS? И остаётся
ли после отката `channel=testing` в конфиге (см. 2.2)?

**Q2. Семантика `Data export` и машиночитаемая диагностика.** Что означают два числа
в `SENDS x/y` и почему `LAST N/A` при `0/1`? Будет ли отдельное состояние для «попыток
ещё не было» вместо зелёного `OK`? Почему в загрузочном логе строка `Send to :` пустая
и во что разворачивается `Default pool (auto)` при `Region = Global`, выведенном «auto
from coordinates» при координатах `0.0,0.0`? Есть ли уже HTTP-эндпоинт со статусом и
последним кодом ошибки в JSON — если да, поддержке хватит его.

**Q3. Штатный путь восстановления и модель доступа.** Каким задуман путь, если
сохранённая сеть исчезла: на загрузке одна попытка ~15 с, дальше `skipping config AP`,
кнопки на этой сборке Urban нет (`Can't setup button pin : -1.00`)? Поднимается ли AP
позже по времени работы? И связанное: локальный UI по умолчанию без аутентификации,
при этом `Download backup` отдаёт ключ, `Restore` принимает чужой конфиг, а
`/guest-restore` доступен на точке настройки — это осознанная модель на время setup
или недосмотр?

**Q4.** Восстанавливает ли `Restore from backup` **identity** устройства (тот же адрес
и, значит, привязку к истории на карте) или только настройки? Без ответа поддержке
нечего сказать каждому, кто нажал `Delete configuration → All settings`, — а с
нынешним дефолтом таких будет много.

**Q5.** Шифрование на ходу: если включить `Encrypt X` на работающем датчике, ряд на
карте станет смесью открытых и зашифрованных значений — график не сломается? И
обратимо ли: после снятия галки новые значения снова публичны, а старые остаются
зашифрованными навсегда?

**Q6.** `Pending sync` у standalone-устройства — что это значит и когда должно
смениться? Сейчас поддержке на это ответить нечем.

## 7. Проверить за две минуты (нам или вам)

- Сохранить настройки, **не трогая пустое поле пароля Wi-Fi** — не затрётся ли
  сохранённый пароль пустым? Классический баг этого паттерна формы.
- Нажать `Delete configuration → All settings` на запасном устройстве: есть ли шаг
  подтверждения и что именно исчезает.
- Открыть UI устройства с телефона гостя в той же сети — убедиться, что `Download
  backup` действительно доступен без пароля.
